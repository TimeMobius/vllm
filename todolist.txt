## 3. 已拒绝候选（不要无证据重复接入）

- [x] **Albatross 风格整块 recurrent kernel**（`csrc/rwkv7_alt_recurrent.cu`）：controlled decode microbenchmark 可约 +106.5%，但 4 prompts × 16 steps 出现 `8 / 64` Top-1 分歧，selected-logprob 最大误差 `3.1454`、common Top-K 最大误差 `9.2296`。根因是 FP32 reduction/accumulation 顺序变化在 61 层递归 decode 中放大；不能作为默认路径。
- [x] **将 `kk * a` inline 到 exact recurrent kernel**：算子 bit-exact，但 C=128 服务约 `705.61 → 705.65 TPS`，无稳定收益，已回退。
- [x] **attention/FFN cache pair gather**：microbenchmark 减少 launch，但 C=128 服务没有稳定优于独立 native gather，已回退。
- [x] **把 PAD remap 移入 native gather**：精度为零误差，但 `clamp + gather` 平均约 `707.23 TPS`，kernel remap 约 `706.57 TPS`，已回退。
- [x] **直接合并 r/k/v 权重为单一 GEMM**：B=32/128 BF16 输出不再 bit-exact（通常相差 1–2 BF16 units），不接入。
- [x] **默认 cublasGemmEx 直接替换 `F.linear`**：isolated `[M,4096] × [4096,4096]` BF16 probe 与 PyTorch bit-exact，但性能仅约 -0.22% 至 +0.34%，无接入价值。
- [x] **cublasLt heuristic/workspace 枚举（2026-08-21）**：在 `M=1/8/32/128, K=N=4096`、0/4/8/64/256 MiB workspace 的 isolated BF16 probe 中，能 `torch.equal` 的候选均与 PyTorch 基线持平量级；C=128 最快 `0.041146 ms` 对 PyTorch `0.041165 ms`（约 +0.05%，低于噪声门限），不接入模型。非精确算法在 M=8/32/128 可出现最高 1–2 BF16 units 的差异。
- [x] **BF16 ordered sparse CMix down projection（2026-08-21）**：按 Albatross 思路实现了 M=1 CUDA-graph-safe 的 tile count/prefix/ordered compact/FP32 accumulation 候选。isolated 94% sparsity时约 `0.160 → 0.111 ms`，服务 C=1 为 `25.74 → 27.38 TPS`（+6.40%），说明 FFN sparse down 的性能潜力真实存在；但 8 prompts × 16 `logprobs=20` 出现 `2 / 8` text/token 分歧、selected max `2.630697`、common Top-K max `11.437075`。FP32 accumulation 和 index 顺序均不能匹配 PyTorch BF16 GEMV reduction contract，候选已从模型代码移除并恢复严格稳定服务。证据：`benchmark_records/20260821_sparse_cmix_bf16_c1_rejected/`。

## 4. 当前性能判断

### 4.1 C=1 与 C=128 是不同目标

- [x] 最新稳定服务（2026-08-21、32 output tokens、temperature=0、`ignore_eos=true`）C=1 三轮为 `25.31 / 25.95 / 25.95 TPS`，均值 **25.74 TPS**；C=8/32/128 aggregate 均值分别为 **158.95 / 460.69 / 705.31 TPS**。
- [x] 因此“50+ TPS”应明确为单请求 C=1 目标，而不是 aggregate C=128。C=128 已远超 50 aggregate TPS，但每请求平均约 5.51 TPS，属排队/批处理吞吐指标，不能与单流 latency 指标混用。
- [x] C=1 Torch profile（31 generation steps）表明三类 BF16 `internal::gemvx` 合计 **984.67 ms**，约占 trace 1.20 s CUDA time 的 **82%**，并有约 **426 个小 linear/step**；下一最大收益点是 decoder 小 projection/FFN down projection，不是 state cache。
- [x] 在同 checkpoint `/hikscale/models/XiaoKe/rwkv-0.pth` 和同 RTX 4090 D 上复现 Albatross C++：`--wkv32 --cmix-sparse off` 为 31.61 raw tok/s，默认 sparse CMix 为 41.15 raw tok/s（+30.2%）。它是 FP16 standalone graph，未经过 vLLM API/sampling 与 BF16 strict logprob 门禁；其 README 的 145+ TPS 是 RTX 5090 的 standalone 结果，不能直接与本机 vLLM C=1 比较。完整证据：`benchmark_records/20260821_single_decode_bottleneck_and_albatross/`。

- [x] 历史 trace（`/tmp/rwkv7_exact_profile_20260821_1616/`）显示：BF16 GEMM/CUTLASS 约 24%，ATen elementwise 约 20%，ATen reductions 约 13%，旧 cache gather/store 约 20%，exact recurrent update 约 9%。
- [x] cache-control 与 recurrent state update 的高价值安全优化已保留；C=128 新 trace 证明大 recurrent state 的 gather/store 仍占约 20.28%，但 copy-only `uint4` 不提升带宽，不能继续堆叠小 cache 算子；下一瓶颈优先是 **decoder projection GEMM/调度** 以及严格 reduction-compatible 的 state materialization 消除。
- [x] 高并发慢的主要风险不只是单个 kernel：C=128 graph replay 同时受 GEMM、逐层 launch/调度、memory traffic、padding/请求调度影响。任何优化必须以服务级 128 并发结果裁决。
