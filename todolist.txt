- [x] unsupported layout、扩展缺失或非 CUDA 情况自动 fallback；copy-only 路径保持 dtype bits。

## 3. 已拒绝候选（不要无证据重复接入）

- [x] **Albatross 风格整块 recurrent kernel**（`csrc/rwkv7_alt_recurrent.cu`）：controlled decode microbenchmark 可约 +106.5%，但 4 prompts × 16 steps 出现 `8 / 64` Top-1 分歧，selected-logprob 最大误差 `3.1454`、common Top-K 最大误差 `9.2296`。根因是 FP32 reduction/accumulation 顺序变化在 61 层递归 decode 中放大；不能作为默认路径。
- [x] **将 `kk * a` inline 到 exact recurrent kernel**：算子 bit-exact，但 C=128 服务约 `705.61 → 705.65 TPS`，无稳定收益，已回退。
- [x] **attention/FFN cache pair gather**：microbenchmark 减少 launch，但 C=128 服务没有稳定优于独立 native gather，已回退。
- [x] **把 PAD remap 移入 native gather**：精度为零误差，但 `clamp + gather` 平均约 `707.23 TPS`，kernel remap 约 `706.57 TPS`，已回退。
- [x] **直接合并 r/k/v 权重为单一 GEMM**：B=32/128 BF16 输出不再 bit-exact（通常相差 1–2 BF16 units），不接入。
- [x] **默认 cublasGemmEx 直接替换 `F.linear`**：isolated `[M,4096] × [4096,4096]` BF16 probe 与 PyTorch bit-exact，但性能仅约 -0.22% 至 +0.34%，无接入价值。
- [x] **cublasLt heuristic/workspace 枚举（2026-08-21）**：在 `M=1/8/32/128, K=N=4096`、0/4/8/64/256 MiB workspace 的 isolated BF16 probe 中，能 `torch.equal` 的候选均与 PyTorch 基线持平量级；C=128 最快 `0.041146 ms` 对 PyTorch `0.041165 ms`（约 +0.05%，低于噪声门限），不接入模型。非精确算法在 M=8/32/128 可出现最高 1–2 BF16 units 的差异。

## 4. 当前性能判断

- [x] 历史 trace（`/tmp/rwkv7_exact_profile_20260821_1616/`）显示：BF16 GEMM/CUTLASS 约 24%，ATen elementwise 约 20%，ATen reductions 约 13%，旧 cache gather/store 约 20%，exact recurrent update 约 9%。
- [x] cache-control 与 recurrent state update 的高价值安全优化已保留；下一瓶颈优先是 **decoder projection GEMM/调度**，而不是继续堆叠 cache 小算子。
- [x] 高并发慢的主要风险不只是单个 kernel：C=128 graph replay 同时受 GEMM、逐层 launch/调度、memory traffic、padding/请求调度影响。任何优化必须以服务级 128 并发结果裁决。
